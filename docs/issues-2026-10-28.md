## Issue #25：已有资料批量重新匹配

以下为实施前方案记录。用户随后批准实施，dev.21 已完成最小版本；当前功能、测试和边界以[订单资料更新教程](order-metadata-update.md)为准。

需求是用中文立创订单 Excel 修正已有元件分类、型号、封装及明确参数，数量不变。评论特别要求减少手动改英文分类。当前服务端尚未实现该订单资料更新工具。

### 可以复用的现有能力

- `server/app/admin/spec_enrichment.py`：按精确 C 料号在线补充官方描述和明确参数，Web 库存页已有入口；不读 Excel，也不重新分类全部库存。
- `server/app/admin/operations.py` 的 `update_component`：现有版本检查、请求幂等和短事务写入；事务内保留当前数量、库位与分配，不生成出入库流水。其现有完整编辑请求字段过宽，需要资料专用字段白名单。
- 认证账户决定数据库位置，Web 库存写入开关仍生效；库存版本变化通过既有同步机制传播。
- Android/Windows `.xls` 订单解析的表头、费用、合计、说明行规则与样例可复用为移植依据；服务端目前没有 Excel 读取依赖，不能直接调用 Kotlin/C# 解析器。

### 建议的最小流程

1. Web 库存页增加“从订单更新资料”。第一版只承诺已有真实导出样本的 BIFF `.xls`，服务端采用与格式对应的 Python 读取库；不把改扩展名当成格式兼容。
2. 只读预览：`POST /admin-api/components/order-metadata/preview`。按标准化后的精确 C 料号匹配当前账户活动元件；不创建元件。显示来源行、当前值、新值、未匹配项、同 SKU 资料冲突。数量列只供核对来源，不进入更新 payload。
3. 用户选择条目和字段。默认保留用户名称、SKU、图片关联、自由备注；优先可选中文分类、封装、明确的型号/品牌/参数。表内空值不清除已有值。同 SKU 多条记录资料冲突时要求人工选定，不按最后一行覆盖。
4. 确认应用：`POST /admin-api/components/order-metadata/apply`。白名单仅含允许的资料字段，每项带 ID、`expected_updated_at` 和幂等 request ID。数量、库位、分配、最低库存、删除状态与流水不在允许字段中。
5. 逐项短事务读取当前元件并检查版本；未选字段取事务内当前值。成功、无变化、冲突和失败分别返回，失败不撤销其他成功项，重试只处理未完成项。首版无需后台任务调度或长期保存原始订单文件。
6. 完成后提示“服务端资料已更新，请设备同步”。同步成功后设备获取新资料，不能把服务端提交成功写成全部设备已完成。

### 中文分类与电气参数

订单中的中文商品分类应作为可预览候选。没有分类时可提供明确标注的在线查询补全，但不能用英文结果静默覆盖已有中文或用户分类。表格未明确给出的容量、阻值、耐压等不能仅从型号猜测。参数继续采用项目已有 `参数·键：值` 格式，按被选择的资料行更新 description，保留用户备注与图片标记；第一版无需增加独立参数表或迁移库存 schema。

### 并发与同步边界

预览后若发生出入库或其他资料编辑，`updated_at` 会变化；应用应返回该项冲突、要求重新预览，不能拿旧整行回写，也不能悄悄使用最新版本强制重试。当前受管库存同步存在 `base_updated_at` 冲突检查，旧标量快照仍有整行 LWW 路径，因此“此资料操作不改数量”可以严格实现，“所有离线旧设备并发同步后永不覆盖”不能仅靠新工具保证。建议先同步各设备的待提交变更，再批量更新资料，冲突时逐项核对；不在本任务中顺带重写字段级同步协议。

最小验证包括：真实格式解析与说明行、重复 SKU 资料冲突、字段白名单和空值策略、数量/库位/分配/流水不变、版本冲突、幂等重试及账户隔离。完整跨设备验收应在实施后独立完成。
